# Milkrice sync format, version 1

This is the byte-level spec of Milkrice's end-to-end encrypted sync between the Mac app and the
iPhone app. It is written so that a second implementation (Swift with CryptoKit) can interoperate
with `crates/milkrice-sync` without reading the Rust code. The test vectors in
[`crates/milkrice-sync/tests/vectors/v1.json`](../crates/milkrice-sync/tests/vectors/v1.json) are
generated by that code and checked by `cargo test -p milkrice-sync --test vectors`. An
implementation is conforming when it reproduces every vector (§9).

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Model

* A **vault** is one folder that every device can read and write: iCloud Drive › Milkrice Sync by
  default, or any synced folder (Dropbox, Google Drive, Syncthing…). There is no Milkrice server.
* The vault has one 32-byte symmetric **vault key**. Every paired device holds it in its keychain.
  It never appears in the folder in the clear.
* Each device has a **device id** and writes only files named after itself, so storage providers
  never create "conflicted copy" files.
* Anyone who can write to the folder (the storage provider, another app, someone with the cloud
  login) is treated as an attacker who doesn't have the key. They can read file names, sizes and
  times, and delete, copy, rename, roll back or plant files. They can't read or forge contents.

## 2. Primitives and encodings

| Name | Definition |
| --- | --- |
| AEAD | ChaCha20-Poly1305, RFC 8439: 32-byte key, 12-byte nonce, 16-byte tag. CryptoKit: `ChaChaPoly`. |
| DH | X25519, RFC 7748. CryptoKit: `Curve25519.KeyAgreement`. |
| KDF | HKDF-SHA256, RFC 5869. CryptoKit: `HKDF<SHA256>`. |
| MAC | HMAC-SHA256. CryptoKit: `HMAC<SHA256>`. |
| `b64(x)` | base64url (RFC 4648 §5) **without padding**. Decoders MUST accept surrounding whitespace and reject padding characters `=`. Foundation's `Data(base64Encoded:)` is standard base64: map `-`→`+`, `_`→`/` and re-pad before decoding. |
| `hex(x)` | lowercase hexadecimal. |
| `u32be(n)` | 4 bytes, big-endian. |
| `‖` | byte concatenation. |
| Random | 32-byte keys and secrets, 16-byte ids and 12-byte nonces MUST come from a CSPRNG (`SecRandomCopyBytes`, or CryptoKit's own key generation). |

All JSON is UTF-8. Readers MUST ignore unknown object members (they're how later versions add
things) and MUST NOT depend on member order or whitespace.

## 3. Folder layout

```text
<vault>/vault.json                         public header (§4), not encrypted
<vault>/devices/<device id>.dev            sealed device card (§6.2)
<vault>/m/<meeting id>/<device id>.rec     sealed record: that device's view of one meeting (§6.1)
<vault>/pair/<session hex>.req             pairing request, short-lived (§8)
<vault>/pair/<session hex>.resp            pairing response, short-lived (§8)
```

**Ids.** Meeting ids and device ids MUST match `^[A-Za-z0-9._-]{1,128}$` and MUST NOT be `.` or
`..`. Meeting ids are lowercase UUIDs today; Mac device ids are `hex(16 random bytes)`. A device
id SHOULD be 32 random hex characters. Readers MUST skip any name that doesn't match this rule.

**Writing.** Write to a new, uniquely named temporary file in the same folder, opened with
exclusive create (`O_CREAT|O_EXCL`, which fails if anything, including a symlink, is already at that path;
Foundation: `FileManager.createFile` is *not* exclusive, use `open(2)` with `O_EXCL`), then rename it over the final name.
Temporary names MUST NOT end in `.rec`, `.dev`, `.req` or `.resp`. The Rust code uses
`.<final name>.<16 hex>.tmp`. A writer MUST NOT create or write through a symbolic link anywhere
below the vault folder.

**Reading.** Readers MUST skip symbolic links and anything that isn't a regular file, and MUST
NOT read more than 64 MiB from a sealed file (1 MiB for device cards, 16 KiB for pairing files,
64 KiB for `vault.json`). Unreadable or unauthenticated files are skipped and reported, never
fatal for the whole sync.

## 4. `vault.json`

```json
{ "format": 1, "vault_id": "<b64, 16 bytes>", "key_id": 1, "kcv": "<16 hex chars>" }
```

* `format`: this spec is format `1`. A device MUST refuse to use a vault whose `format` it
  doesn't know (an older app must not write old-format files into a newer vault).
* `vault_id`: 16 random bytes, fixed for the life of the vault.
* `key_id`: label of the current vault key, written into every sealed header. `1` today.
* `kcv` (key check value): `hex(HMAC-SHA256(key = vault key, msg = "milkrice-kcv-v1")[0..8])`.
  Lets a device tell "I hold the wrong key" from "this file is damaged".

`vault.json` is **not authenticated**: anyone with folder access can rewrite it. A device MUST
therefore remember the vault id it paired with and refuse to sync if `vault.json` names another
one (`Vault::open_expecting`), and MUST check the KCV against its key before writing anything.

## 5. Sealed files (`.rec`, `.dev`)

```text
offset  size  field
0       4     magic "MRS1" (4d 52 53 31)
4       16    vault_id
20      4     key_id, u32 big-endian
24      12    nonce (random per file)
36      n     ciphertext, n = len(padded plaintext), a multiple of 1024
36+n    16    Poly1305 tag
```

* `header` = bytes 0..24. It is the AEAD **associated data**, so a file can't be moved to another
  vault or relabelled with another key id.
* `padded plaintext` = `u32be(len(payload)) ‖ payload ‖ zero bytes` up to the next multiple of
  1024 bytes (`ceil((4 + len) / 1024) * 1024`; an empty payload pads to 1024). This hides exact
  lengths from the storage provider.
* `ciphertext ‖ tag` = `ChaCha20-Poly1305-Encrypt(key = vault key, nonce, aad = header, padded)`.
* In CryptoKit, bytes 24..end are exactly `ChaChaPoly.SealedBox.combined`:
  `try ChaChaPoly.SealedBox(combined: file[24...])`, then
  `ChaChaPoly.open(box, using: key, authenticating: file[0..<24])`.

**Opening.** In this order: length MUST be > 52 bytes (24 + 12 + 16); magic MUST be `MRS1`;
`vault_id` MUST equal the vault's id; then authenticate and decrypt (no plaintext is looked at
before the tag checks); then read `L = u32be(plain[0..4])`, require `4 + L ≤ len(plain)`, and the
payload is `plain[4..4+L]`. Readers SHOULD use `key_id` only to choose a key.

The payload is UTF-8 JSON (§6). Nonces are random, so a device MUST NOT seal with a fixed or
counter nonce: two devices share the key.

## 6. Payloads

### 6.1 Records (`m/<meeting id>/<device id>.rec`)

One device's full current view of one meeting:

```json
{ "v": 1, "id": "<meeting id>", "device": "<device id>",
  "fields": { "<name>": { "v": <any JSON>, "hlc": "<HLC>" }, ... } }
```

A reader MUST check that `id` equals the folder name and `device` equals the file name (minus
`.rec`), and skip the file otherwise: the sealed contents are what bind a file to its path, so a
copy under another name is rejected. A device MUST NOT treat a file under its own device id as a
remote record.

Fields that sync (readers ignore any other field name; version 1 does not carry unknown fields forward):

| Field | Value |
| --- | --- |
| `title`, `notes`, `enhanced` | string |
| `enhanced_by`, `transcribed_by` | string (model names) |
| `transcript` | array of `[start_ms, end_ms, speaker, text]` |
| `created_at` | RFC 3339 string, seconds, `Z` |
| `duration_ms` | integer |
| `mode` | string: `"mac"`, `"room"`, `"voice note"`… |
| `origin` | string: `"mac"` or `"iphone"` |
| `deleted` | boolean; `true` is a tombstone |
| `notes_request` | string; a phone asking the Mac to write notes (§7.5) |

### 6.2 Device cards (`devices/<device id>.dev`)

```json
{ "name": "Studio Mac", "kind": "mac", "last_seen": "2026-11-27T09:00:00Z" }
```

`last_seen` MAY be absent. The card does not name its device id, so a card can be swapped with
another device's card by someone with folder access; cards are display-only and MUST NOT drive
any security decision.

## 7. Merge

### 7.1 Hybrid logical clocks (HLC)

An HLC is the ASCII string

```text
<ms: 13 decimal digits, zero-padded>-<counter: 4 decimal digits, zero-padded>-<device id>
e.g. 1763683200000-0000-phone0000000000000000000000000001
```

**Parsing** (`parse_hlc`). Split on the first two `-`. `ms` and `counter` MUST be 1–20 ASCII
digits; `ms ≤ 9999999999999`; `counter` MUST fit in a u32; the device part MUST be a valid id
(§3). Anything else is **malformed**. (Parsers accept counters wider than 4 digits only because
an earlier build could write them; writers never do.)

**Order** (`hlc_cmp`). Compare parsed `(ms, counter, device)` lexicographically, with `device`
compared byte-wise. Malformed stamps sort before all valid ones. For stamps a conforming writer
produces this equals byte-wise string order, so a Swift implementation MAY compare strings only
if it never accepts a counter wider than 4 digits; using the tuple is simpler and safer.

**Clock state** per device: `(ms: u64, counter: u32)`, starting at `(0, 0)`, persisted.

* `tick(wall_ms)`: if `wall_ms > ms` then `ms = wall_ms, counter = 0`; else if `counter ≥ 9999`
  then `ms = ms + 1, counter = 0`; else `counter += 1`. Return
  `format("%013d-%04d-%s", ms, counter, device)`. (`wall_ms` is clamped to `9999999999999`.)
* `observe(hlc)`: if `hlc` is malformed, do nothing. Otherwise if `(h.ms, h.counter) > (ms,
  counter)` set `ms, counter` to them.

Vectors: `hlc.tick_overflow`, `hlc.observe`, `hlc.valid`, `hlc.invalid`, `hlc.compare`.

### 7.2 Value hash

`value_hash(v) = hex(SHA256(canonical(v))[0..8])` with this canonical encoding:

| JSON | Bytes |
| --- | --- |
| `null` | `n` |
| `true` / `false` | `b1` / `b0` |
| number that is an integer in i64 range | `i` ‖ decimal ‖ `;` (e.g. `i-5;`) |
| any other number | `f` ‖ Rust `f64` `Display` ‖ `;` (avoid: see below) |
| string | `s` ‖ decimal(UTF-8 byte length) ‖ `:` ‖ UTF-8 bytes |
| array | `a` ‖ decimal(count) ‖ `[` ‖ items ‖ `]` |
| object | `o` ‖ decimal(count) ‖ `{` ‖ for each key in **byte-wise UTF-8 order**: canonical(key as string) ‖ canonical(value) ‖ `}` |

Swift notes: use `s.utf8.count`; sort keys with `Array(k.utf8).lexicographicallyPrecedes`, not
`<` (Swift's `String <` is Unicode-aware). Version 1 fields never hold non-integer numbers; a
writer MUST NOT put them in synced fields, because float text differs between languages and
`1.0` vs `1` would hash differently. Vector: `canonical`.

### 7.3 Per-device state

For each meeting a device keeps `state: {field → {hash, hlc}}`: the hash of the value it last
saw or wrote for that field, and that value's HLC.

### 7.4 The merge of one meeting

Inputs: the meeting `id`; `local` (this device's current values, a map field → value; fields
the device doesn't hold are absent); `state` (§7.3, updated in place); `remotes` (other devices'
records for the meeting, any order); the clock; `wall_ms`.

1. For every field of every remote record, `observe(hlc)`.
2. **Local edits.** For each `(name, v)` in `local` with `name` a synced field, in ascending
   byte-wise order of `name`: if `state[name]` is absent or `state[name].hash ≠ value_hash(v)`,
   set `state[name] = {hash: value_hash(v), hlc: tick(wall_ms)}`.
3. **Remote values.** `values = copy(local)`, `apply = {}`. For each remote record with
   `record.id == id`, for each `(name, {v, hlc})` in its fields (in ascending order of `name`)
   where `name` is a synced field and `hlc` is not malformed: if `state[name]` is absent or
   `hlc_cmp(hlc, state[name].hlc) > 0` then
   * `state[name] = {hash: value_hash(v), hlc}`;
   * if `values[name]` is absent or `value_hash(values[name]) ≠ value_hash(v)`, set `apply[name] = v`;
   * `values[name] = v`.
4. **Our record.** `{v: 1, id, device: <own id>, fields: {name: {v: values[name], hlc: state[name].hlc}}}`
   for every `name` in `values` that has a `state` entry.
5. The device applies `apply` to its store and writes the record (if it has any fields) to
   `m/<id>/<own id>.rec`. A writer SHOULD skip the write when the record is unchanged.

Properties (checked by `tests/merge_props.rs`): the result doesn't depend on the order of
`remotes`; merging the same input twice changes nothing; once all devices have synced twice
with no new edits, they hold identical values, each field holding its newest-HLC write; an
edit made after a device has seen everything always wins.

**Deletes** are the `deleted` field set to `true`, a last-writer-wins tombstone like any other
field. A concurrent edit to another field is kept alongside it, and a later `deleted: false`
restores the meeting with every field intact. A device that deletes a meeting locally writes a
record holding `deleted: true`. Record files are not removed from the folder when a meeting is
deleted: the tombstone record is what tells devices that were offline.

Vectors: `merge[]`: each case gives the inputs (`local`, `state`, `remotes`, `clock`,
`wall_ms`) and the expected `apply`, `record`, `state` and final `clock`.

### 7.5 Notes requests

A phone sets `notes_request` to a non-empty string to ask the Mac for AI notes. The Mac treats
the request as pending when `state.notes_request.hlc` is newer (by `hlc_cmp`) than
`state.enhanced.hlc` (or `enhanced` has no state) and the newest remote `notes_request` value is
a non-empty string.

## 8. Pairing protocol

Pairing gives a new device (the **phone**) the vault key, with the folder as the only channel
besides a QR code shown on the Mac's screen. The QR code is the authentic channel; a 6-digit code
shown on both screens catches anyone who photographed it.

### 8.1 Invite (QR code)

The Mac makes an ephemeral X25519 key pair `(mac_secret, mac_pub)` and an 8-byte random `session`,
and shows the QR code text

```text
milkrice-pair:1:<b64(vault_id)>:<b64(session)>:<b64(mac_pub)>
```

Parsers MUST require the exact prefix `milkrice-pair:1:`, exactly three `:`-separated parts, and
decoded lengths 16, 8 and 32. `session_hex = hex(session)` names the pairing files. The invite
expires 10 minutes after it is shown; after that the Mac MUST refuse to read requests or grant.
On starting a pairing the Mac MAY delete `pair/` files older than one hour.

### 8.2 Key derivation (both sides)

```text
shared   = X25519(own_secret, peer_pub)              -- MUST NOT be 32 zero bytes (reject)
salt     = vault_id(16) ‖ session(8) ‖ mac_pub(32) ‖ phone_pub(32)       -- 88 bytes
prk      = HKDF-Extract(salt, shared)
pair_key = HKDF-Expand(prk, info = "milkrice-pair-key-v1",  L = 32)
c        = HKDF-Expand(prk, info = "milkrice-pair-code-v1", L = 4)
code     = format("%06d", u32be⁻¹(c) mod 1000000)
```

In CryptoKit: `shared.hkdfDerivedSymmetricKey(using: SHA256.self, salt: salt, sharedInfo: info,
outputByteCount: n)` once per `info`. Check the shared secret is not all zeros yourself
(`shared.withUnsafeBytes { $0.allSatisfy { $0 == 0 } }`) rather than relying on the platform to
reject low-order public keys; vector-checked in `tests/pairing.rs` (`low_order_public_keys_are_refused`).

### 8.3 Request: `pair/<session_hex>.req` (phone → Mac)

The phone scans the QR, checks that `vault.json` (if present) has the same `vault_id` and a known
`format`, makes its own ephemeral key pair, derives §8.2 and writes:

```json
{ "v": 1, "pub": "<b64(phone_pub)>", "card": "<b64(box)>" }
box = nonce(12) ‖ ChaCha20-Poly1305(key = pair_key, nonce, aad = session(8), msg = card JSON)
card JSON = {"name": "<device name>", "kind": "iphone"}
```

`box` is CryptoKit's `SealedBox.combined`. The phone shows `code`.

### 8.4 Mac side

The Mac polls for the request file. A file that isn't complete JSON yet is waited out. For a
parsed request it MUST check `v == 1`, decode `pub` (32 bytes), derive §8.2, and open `card`; a
request that fails any check is an error and is not remembered. The **first** request that
authenticates is kept for the rest of the attempt; later requests are ignored. The Mac shows the
device name (after removing control and bidi-override characters, at most 64 characters) and
`code`, and asks the person whether the codes on both screens match.

### 8.5 Response: `pair/<session_hex>.resp` (Mac → phone)

Only after the person confirms, and before the invite expires, the Mac writes:

```json
{ "v": 1, "grant": "<b64(box)>" }
box = nonce(12) ‖ ChaCha20-Poly1305(key = pair_key, nonce, aad = session(8), msg = u32be(key_id) ‖ vault_key(32))
```

and deletes the request. On cancel, the Mac deletes the request and writes nothing.

### 8.6 Phone side, finishing

The phone polls for the response, requires `v == 1`, opens `grant` (plaintext MUST be exactly 36
bytes), and before storing the key MUST check that `vault.json`'s KCV matches the received key,
`format` is known, and `vault_id` equals the QR's. It then stores `(vault_id, key)` in its
keychain, deletes the response, and writes its device card (§6.2).

### 8.7 What the code protects against

* Someone with folder access but no QR doesn't know `mac_pub`, so cannot produce a request the
  Mac can open; they can only delay pairing by overwriting the request file.
* Someone who photographed the QR and also writes a request makes the Mac show a code derived
  from *their* key. They can compute that code but not the real phone's (they don't hold either
  secret), so the two screens disagree except with probability 10⁻⁶ per attempt.
* A response from another session doesn't open (different `pair_key`; `session` is bound as AAD).

The reference state machines are `pairing::Pairing` (Mac) and `pairing::Joiner` (phone).

## 9. Test vectors

`crates/milkrice-sync/tests/vectors/v1.json`. Byte strings are hex unless the key says `b64`/`qr`.
Fixture bytes are `byte[i] = seed + 7·i (mod 256)` with a per-value seed.

| Key | What to check |
| --- | --- |
| `seal` | `seal(key, vault_id, key_id, nonce, payload)` gives `file` byte for byte, and `open` gives `payload`. |
| `pad[]` | Sealing `payload_len` bytes of `x` with the `seal` key, vault id, nonce and `key_id = 1` gives a file of `file_len` bytes whose SHA-256 is `sha256` (padding boundary at 1020/1021). |
| `kcv` | `kcv(key)`. |
| `canonical` | `canonical(value)` is `encoding_hex`; `value_hash(value)` is `hash`. |
| `pair` | From `mac_secret`/`phone_secret`: the public keys, `qr`, `pair_key` and `code` on both sides; `seal_grant` with `grant_nonce` gives `grant`; the card box with `card_nonce` over `card_plain` gives `card`. |
| `pair_messages` | The exact `.req` and `.resp` file contents for the `pair` vector (`req_json`, `resp_json`). Compare parsed JSON, not bytes. |
| `hlc` | `tick_overflow`: three ticks from the given clock at `wall_ms` give `ticks`. `observe`: after observing `observed` (then the malformed `then_garbage`), a tick at the given wall time gives the value shown. `valid`/`invalid` parse or don't. `compare`: `[a, b, sign(hlc_cmp(a, b))]`. |
| `merge[]` | §7.4 on the inputs gives `expect` exactly (`apply`, `record`, `state`, `clock`). |

## 10. Versioning

* The sealed-file magic `MRS1`, `vault.json` `format: 1`, record `v: 1`, the QR prefix
  `milkrice-pair:1:` and request/response `v: 1` are independent version markers.
* A change readers of this version can't safely ignore MUST bump `vault.json`'s `format`, and
  readers MUST refuse unknown formats (§4). Adding fields to records or cards does not need a bump.
* Planned for a format 2 (not yet specified): per-purpose subkeys from the vault key via HKDF,
  the record path and file kind in the associated data, separate AEAD labels for the two pairing
  directions, the device id inside device cards, and key rotation (re-keying when a device is
  removed). See `docs/audits/sync-security-review-2026-11.md`.
